# 07 · UUID Strategy

**Status:** Blueprint (no implementation).
**Basis:** TRD §8 ("Use UUID v7 for primary keys"), `004` (UUID primary keys).

## 1. Decision

**Every table's primary key is a UUID version 7.** Auto-increment / serial integer
keys are **not used anywhere.**

## 2. Why not auto-increment integers

| Problem with serial IDs | Consequence |
| --- | --- |
| **Enumerable** (`/orders/1042`) | Competitors/attackers can scrape catalog size, order volume, and walk records (IDOR risk) — bad for a business that guards order/customer data (BRD §20). |
| **Reveals business volume** | Sequential order/customer IDs leak growth metrics to anyone. |
| **Merge/replication collisions** | Two databases (staging↔prod, future sharding, offline import) generate the same `123` → conflicts. |
| **Client/distributed generation impossible** | IDs can only be assigned by the DB on insert, complicating pre-generation, optimistic UI, and event sourcing. |
| **Hard to scale out** | Sharding/partitioning and multi-region (future i18n) need globally-unique keys without a central sequence. |

UUIDs solve all of the above: globally unique, non-enumerable, client-generatable,
shard-friendly.

## 3. Why UUID **v7** specifically (not v4)

| | UUID v4 (random) | **UUID v7 (time-ordered)** |
| --- | --- | --- |
| Layout | 122 random bits | 48-bit Unix-ms timestamp + random |
| Sortability | none | **k-sortable** (roughly chronological) |
| B-tree insert locality | random → page splits, fragmentation, cache misses | **sequential → right-edge inserts**, less bloat |
| Write throughput at scale | degrades | **stays healthy** (matters at 10k orders/day) |
| Leaks creation time | no | yes (acceptable; not a secret) |

**Why v7 over v4:** v4's randomness fragments every index it keys; at FWorld's
target scale (100k products, 1M users, 10k orders/day) that means slower inserts
and bloated indexes. v7 keeps the **non-enumerable** security benefit of UUIDs
**and** the **insert locality** of sequential keys — the best of both. It also
gives a natural creation-time ordering for keyset pagination ([05](./05-indexing-strategy.md)).

## 4. Storage

- Stored as the **native `uuid`** type (16 bytes), **not** `text` (which would be
  36 bytes + slower compares). Indexed as the primary key.

## 5. Generation — ⚠ open decision (DB-13)

`UUID v7` generation must be settled before implementation:

| Option | Note |
| --- | --- |
| **App-level (recommended now)** | Generate v7 in the Node/NestJS layer (a v7-capable UUID utility) and pass it on insert. Works on **any** PostgreSQL version. **Why recommended:** the compose stack pins **`postgres:16`** (ADR-0001 / docker-compose), and native `uuidv7()` only ships in **PostgreSQL 18+**. |
| DB-native `uuidv7()` | Cleanest, but requires upgrading the database to **PostgreSQL 18+**. |
| Extension (e.g. `pg_uuidv7`) | DB-side generation on PG 16/17 via an extension — adds an infra dependency. |

> **Conflict DB-13:** TRD §8 mandates UUID v7, but the provisioned database is
> PostgreSQL 16, which has no native v7. **Also:** Prisma's default `@default(uuid())`
> generates **v4** — v7 will require explicit app-side generation or a DB default,
> not the Prisma default. **Requires CTO decision** (app-gen vs PG upgrade vs
> extension) before any schema work.

## 6. Consequences

- All FKs are `uuid`; all PKs are `uuid`.
- IDs may be **generated by the application before insert** (enables optimistic
  creation, idempotency keys, and event-carried state).
- Public URLs/refs may still prefer opaque business keys (e.g. `orderNumber`,
  `slug`) over raw UUIDs for friendliness — UUID remains the internal PK.
